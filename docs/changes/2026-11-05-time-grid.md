# Handoff Note

- Date: 2026-11-05
- Agent: Code
- Topic: the Plan screen as a 30-minute grid

## Summary

The Plan screen no longer plans a day as an **order**. Every half hour from Day
Start to Day End is a box, drawn whether it holds anything or not, and a block
stores **which box** it is in (`time_blocks.slot_index`) relative to Day Start.
The clock times follow from the box on read.

Three decisions settled by Dave before the build, and the model is them:

1. **Fixed grid, drop on a box.** Gaps are a legitimate day. Nothing ever
   slides up to close one.
2. **Odd lengths round up.** A 45-minute task occupies two boxes, keeps its own
   45 minutes (it ends 09:45), and the second box says `15m spare`.
3. **A box is worth 30 minutes however many tasks are in it** — up to four.

What that buys, and the reason the change was worth making rather than
patching the order model:

- **A Day Start change writes nothing.** `slot_index` is relative to Day Start,
  so moving it re-times every planned day on every date by writing zero rows.
  This is what retired `repack_all_days`, the "this day is too full to re-time"
  refusal, and the transaction that could leave one day derived from one set of
  bounds and another from a different set.
- **A move is an assignment, not a shuffle.** A drag writes one row's box. It
  retired `reorder_time_blocks`, `move_block`, `move_block_to_gap`,
  `sort_blocks` and `renumber`.
- **`span` is derived, never stored.** `ceil(planned_minutes / 30)`. Two columns
  that can disagree is P6.
- **`slot_index` is nullable with no default.** `NULL` means "never placed",
  which is a different fact from "box 0". A default of 0 would have piled every
  unplaced block onto 08:00.

Work the grid cannot hold is **surfaced, never dropped** (P2): a block whose box
is past a Day End moved earlier, whose length now runs off the end, that lunch
has since moved onto, or that has never been placed, is drawn in an *Outside the
day (n)* group under the grid, and dragging it onto a box places it. Days
planned under the old model are adopted on first open: a **readable start time
goes on the box that time names or nowhere**, never slid to the nearest free
box, because that would move planned work to an hour nobody picked.

Every refusal names itself — outside the day, running into lunch, that half hour
full — and writes nothing. A release in the day column but on no box creates
nothing and says *Drop an item on a half-hour box*: the app does not choose an
hour.

**TG-M8.3 was dropped, not implemented.** The sliver bug the step was ordered
for **does not reproduce**: `test_tgm81`/`test_tgm82` passed against unmodified
code, and a probe measured a row at 667px inside a 671px pane in the real Plan
screen. The rationale was false too — `_aim_pointer_at`'s `max(1, w // 2)`
alters the aim only at widths 0 and 1. No fix was written and none is claimed.
The two width tests were kept and moved onto the grid pane, because the property
they pin had no coverage at all: every other geometry test asserts *behaviour*,
and a row collapsed to a sliver satisfies all of them.

### Fixed in the sweep

- **High (P1 + P6): adoption could write a guess down permanently.**
  `AppSettings.load()` returns an all-defaults object when a settings file
  exists but cannot be parsed, and the caller could not tell that from a
  genuine fresh install. `adopt_legacy_day` then converted legacy clock times
  into `slot_index` values against that guessed Day Start and overwrote
  `start_time`, the only record of what the user had chosen — a recoverable
  read failure becoming an unrecoverable write. `load` now flags the
  fallback, the screen declines to adopt on a day shape it cannot trust, and
  the blocks wait in the *Outside the day* group, which is the retryable state
  that already existed. Adoption also now *reports* itself, naming the Day
  Start it used: the ids it returns were being discarded, so the one
  irreversible step in the feature was the only silent one.
  - Not treated as a defect: that a later Day Start change re-times adopted
    blocks. That is the approved design (a box is stored relative to Day
    Start), not a bug, and re-opening it on a reviewer's say-so would have
    changed a decision the user made.
- **Medium: every continuation box claimed the last box's spare minutes.**
  A 75-minute task read `15m spare` on both the second and third box, though
  the second is consumed whole. Found by both passes. Gated on the final
  continuation.
- **Medium: a task dragged off a box was silent.** The item branch of
  `on_drag_release` reported this; the block branch had no `else` at all, so a
  release over the heading, the summary or the *Outside the day* group did
  nothing and said nothing.
- **Medium: a raw row id reached the status line.** Choosing a length for a
  block in the *Outside the day* group — an ordinary gesture, since that group
  binds the same menu — showed `time block '<uuid>' is not on the grid`.
  Refused in the screen's own words now.
- **Medium: most of an *Outside the day* row was dead to the mouse.** That
  group wraps its chip in a holder, so its title and minutes labels sit two
  levels below the bound widget, and `bind_block_handlers` bound only direct
  children. A press on the title — most of the row — started nothing, in the
  one group the screen tells the user to drag blocks out of. Handlers are now
  bound to the whole subtree, which also closes the pre-existing "a depth bar
  is not draggable" backlog item.
- **Medium: a resize silently reordered its box.** `_settle_block_on_slot`
  reassigned `position` on every call, so resizing the first of two tasks
  sharing a box moved it below the second — from a function whose docstring
  says it keeps the block where it is. Only a change of box renumbers now.
- **Medium (P6 / rule 13): eight `docs/spec_coverage.md` rows named deleted
  tests**, two of them still marked `done`. The cold pass found two; extending
  `tests/test_traceability_refs.py` to scan that document found all eight. The
  guard had never covered the one document most made of the references it
  checks, which is why the class went unnoticed. A retired criterion now keeps
  its history as a plain backticked test name rather than a `tests/...::name`
  pointer a reviewer would follow to nothing.
- **Documentation the batch had missed**, found by auditing it rather than by a
  pass: `README.md` still described the order model in four places (the feature

## The re-sweep of the fix commits

The sweep's own fixes were mutation-proved but not themselves reviewed, so the
three fix commits went through `learning-qa` again as their own range
(`56b3ba6...HEAD`, 1139 lines). It was worth doing: **one high and four medium
findings, in code written forty minutes earlier.**

- **High (P6/P1): the flag the first round added was never cleared.**
  `load()` set `settings_unreadable`; nothing unset it. The documented recovery
  — the status line says Day Settings could not be read, the user opens Day
  Settings and saves — left the flag set, so adoption stayed blocked, and the
  screen then reported *"Day settings saved"* over it. The only way out was
  relaunching the app, which nothing in the UI or the guide mentions. A
  successful write now clears the flag, because a readable file holding exactly
  these values is what makes it false.
- **Medium-high, and pre-existing: `save()` replaced an unreadable settings
  file with defaults and kept no copy.** It behaved that way before this batch
  existed; the flag is what makes it detectable. Saving is how the user gets a
  working file back, but it writes *every* setting, so the old file was the only
  copy of anything the app could not read out of it. It is now copied to
  `settings.json.unreadable-<date>-<time>` first, and a failed write returns
  `False` instead of being swallowed — which the Day Settings dialog acts on, so
  it no longer reports a save that did not happen. The other settings screens
  still do; that is in `BACKLOG.md` as adjacent, because it touches every
  settings surface and belongs in its own diff.
- **Medium: four `docs/spec_coverage.md` rows still marked `done` named
  functions that no longer exist** (`repack_day`, `reorder_time_blocks`,
  `block_height`). The same defect the first round fixed, one column over: the
  guard extended to that document checks test pointers, not source ones. Seven
  deleted names in all, now marked as history. Extending the guard to source
  symbols is in `BACKLOG.md`.
- **Medium: the unreadable-settings warning fired with nothing to be about.**
  The branch had no condition on there being anything to adopt, so every date
  change on an ordinary day warned about blocks from an earlier version that did
  not exist — and it was written off `_day_shape_is_the_users()`, which is also
  false when no settings object was supplied at all, a wiring mistake that sent
  the user to a dialog that would not help.
- **Medium: the position guard went into the shared helper, not the caller whose
  bug it was.** `_settle_block_on_slot` is used by `add_block_at`,
  `place_block_at`, `set_block_length` and `adopt_legacy_day`. Guarding it
  turned a drop onto the box a block is already in — `place_block_at`'s
  documented nudge, and the only ordering gesture a box has — into a no-op,
  while the screen still said *"Moved to …"*. It is a `keep_position` argument
  now, passed only by the resize.

Five fixes, nine new tests, **10 mutations and 10 reds**. Six below-medium
findings went to `BACKLOG.md` with their severity.

Two things worth keeping from this round. The high finding is a fix that was
half a fix: the first round correctly refused to write a guess, and left the
user with no way to stop refusing. And the medium on `spec_coverage` is the same
defect class twice in one batch, found both times by widening a check rather
than by looking harder — the first round's own guard extension is what made the
second one cheap.

## The third pass, and the fix that made things worse

The second round produced a high, so the budget called for another pass: cold
again, and a different failure family — correctness and test quality rather
than the pattern catalogue. **It produced another high, in the round-2 fix.**

- **High: clearing the unreadable flag on *any* successful write re-opened the
  guard it was built to close.** Round 2 cleared it inside
  `AppSettings.save()`, reasoning that a written file holds exactly these
  values. But every settings screen loads its own `AppSettings`,
  `screens/settings.py` saves the whole object and then *replaces*
  `app.settings` with its copy, and `app.show_plan()` builds a fresh
  `PlanScreen` from that object on every navigation. So changing the **theme**
  on a corrupt settings file cleared the flag, and the next visit to Plan ran
  `adopt_legacy_day` against a guessed 08:00 and overwrote every legacy
  block's stored time — the exact P1 write round 1 added the guard for, now
  reachable from a surface that never showed the user a day setting, in the
  same session. The flag is cleared by the Day Settings dialog now, the one
  place that shows the day's four times and takes the user's confirmation of
  them.
- **Medium: the dialog left the app-wide settings object mutated after a failed
  write.** It sets all five fields before saving; on failure it reported the
  failure and returned, Cancel does not restore anything, and the Plan screen
  is rebuilt from that object — so the next visit drew and timed the day
  against bounds that existed nowhere on disk. The previous values go back now.
- **Medium: a failed backup proceeded to overwrite anyway.** If `copy2` raised,
  the only record was a print and the write went ahead, returning `True` — so
  in the one case the backup exists for, the original was destroyed and the
  user was told the settings were saved. A failed copy refuses the write now.
- **Medium: a status print inside the copy's `try`.** A stdout write that
  failed would read as a copy that failed, and the handler's own print would
  then escape a method whose callers have no handler. The same shape as the
  finding this project's own notes cite from an earlier batch — a status print
  inside a credential `try` that discarded a valid token. Moved out, and
  guarded.
- **Medium (test): the round-2 "end to end" test was not.** It set
  `settings_unreadable` by hand on a settings path that did not exist, which
  skipped both `load()` deciding the file was unreadable and the copy-aside
  branch — the two steps most likely to be wrong. It writes a real corrupt file
  now and asserts the kept copy's contents.
- Two low test findings, both on tests written in the same session: one
  asserted two private predicates where its name was about what the user is
  told, and one asserted only the negative half of the condition it named.
  Both now assert the behaviour they describe.

Five fixes and one new test for the print, **7 mutations and 7 reds.** Two
below-medium findings went to `BACKLOG.md`.

**What this round is evidence for.** Three fix rounds, and the two highs in this
batch were both *in fix commits*, found by cold passes, and neither was the kind
of thing a warm pass finds: round 1's fix refused to write a guess and left no

## The fourth pass: the guard was only session-deep

Cold again, and a family none of the first three had used — the UI contract, run
against `~/.claude/standards/ui-regression.md`. **It produced a fourth high, and
it was right.**

- **High: one relaunch completed the write the batch claims to prevent.**
  Round 3 moved the flag-clear to the Day Settings dialog, which closed the
  same-session route. It did not close the file. `save()` still writes the whole
  object, so the first save from *any* screen — a theme, a column divider on
  Today, a timer window position — wrote a complete set of defaults out as
  ordinary-looking settings. `load()` sets the flag only when a file fails to
  parse, so the next launch read that file, found it fine, and ran
  `adopt_legacy_day` against a day start of 08:00 that nobody had ever chosen.
  The status line then *stated* that guess as the Day Start it had used, and two
  sentences shipped in `CHANGELOG.md` and `docs/USER_GUIDE.md` were false.

  The fix is that the one flag was carrying two facts. They are separate now:
  `settings_unreadable` stays a per-load, in-memory flag whose only job is
  keeping an unparseable file aside before it is overwritten, and a successful
  write clears it, because the file then parses. The new
  `plan_day_shape_unconfirmed` is a **persisted dataclass field** — it goes to
  disk with the defaults it describes, so a relaunch still knows those four day
  values were invented, and only the Day Settings dialog clears it. An old
  settings file without the field reads as `False`, which is correct: a file
  that parses was written by a build that had no guesses to record.
- **Medium: the two save failures shared one message.** "Could not write the
  settings file — see the log" was shown when no write had been attempted and
  `settings.json` was perfectly writable, sending the user to check permissions
  on a file that was fine. `save` reports which failure it was now, and the
  copy failure names the real remedy: move or delete the file yourself.
- **Medium: "Day Settings could not be read" against a file that read fine.**
  The warning was written off the parse flag, which survived on another
  screen's object. It is written off the persisted field now and says what is
  true in every state it can appear in — the day's shape has not been confirmed
  — and it names the one screen that can confirm it, which the old message
  never did.
- **Low: a readable file kept aside as `settings.json.unreadable-<stamp>`.**
  Fixed by the same split: the parse flag is what drives the copy, and a
  successful write clears it.

Nine mutations, nine reds.

**One finding from this pass was not fixed, deliberately.** The new refusal —
`save` returning without writing when an unparseable file cannot be copied aside
— is invisible on the ten call sites that ignore the return value, and on the
appearance screen the user is told *"✓ Saved"*. That is a behaviour regression
on a path that previously wrote, and it is real. It is not fixed here because it
touches every settings surface in the app, and the root cause under it — each
screen loading its own `AppSettings` and saving the whole object — is a change
that belongs in its own reviewed diff. Both are in `BACKLOG.md`, the first
raised in severity with the reason, and `docs/USER_GUIDE.md` warns the user that
other screens will claim to save while this state lasts. The refusal itself
stays: the alternative is destroying the only copy of a file the app could not
read.

## The fifth pass: the upgrade path was the common case, and it was open

Cold, lens: the settings-file format and the state machine around the new
persisted field — the one thing none of the four earlier passes had looked at.
**A fifth high, and it was right.**

- **High: a settings file written before Day Settings existed read as a
  confirmed day.** Time blocks are as old as the application (`5d43ea3`); the
  four day values arrived in `d324217`. Such a file parses perfectly, so round
  4's parse-failure flag never fired, and `load` filters the parsed dict
  against the dataclass fields — which erases the difference between a default
  the user accepted and a default nobody has ever seen. All four values became
  08:00 / 12:00 / 60 / 17:00, `plan_day_shape_unconfirmed` was absent and so
  read as `False`, and the first Plan open ran `adopt_legacy_day` against a day
  start nobody chose, rewriting a stored `09:45` to the `09:30` of its box.
  That is the exact outcome the field was added to prevent, on the normal
  upgrade path rather than an edge case — and the src commit for round 4 stated
  the opposite in as many words: "a file that parses was written by a build that
  had no guesses to record". It was not.
- **Medium: a day value the normalizer had to substitute was treated as the
  user's.** `"25:00"` or a hand-edited `"8am"` is silently replaced so the app
  can start; the substitute then fed the irreversible mapping as a confirmed
  value.
- **Medium: the field is dropped by any build that does not define it.** `save`
  writes `asdict` of the dataclass, so one launch of a packaged app a version
  behind removes the key — and a boolean whose absence meant "confirmed" cannot
  survive that.
- **Medium: `settings_unreadable` was captured at load but described the file.**
  Over a dozen screens each call `AppSettings.load()` and hold their own object,
  while `app.settings` is loaded once at startup and is what the Day Settings
  dialog saves. So: launch on a corrupt file, another screen saves (file kept
  aside, replaced, now parses), then the user opens Day Settings and saves — the
  startup object still carried the flag, archived the good file a second time
  and logged that it could not be read. Worse, if that copy failed the dialog
  refused the write and told the user to move a file that loads, leaving the
  one screen that can confirm the day's shape unable to.

The fix is one rule, in `_day_shape_was_confirmed`: **the day's shape is
confirmed only if the file says so** — `plan_day_shape_unconfirmed` present and
false, all four values present, and nothing substituted on the way in. Absence
is never confirmation, in any path, including no settings file at all. A wrong
"unconfirmed" costs one visit to Day Settings; a wrong "confirmed" rewrites
stored times that nothing can recover, so the default is the cheap mistake.
`settings_unreadable` is gone — nothing read it after round 4 — and `save` now
asks the file itself whether it parses before copying it aside (P6).

Ten mutations, ten reds, and two things worth recording about the gate:

- The first attempt showed **green over a mutation twice**. For a
  pre-Day-Settings file the key-presence check and the confirmation-key check
  each suffice, so neither single mutation could red the test — the test was
  real, but it was proved by the pair, not by the line it named. Fixed by
  mutating the whole decision for those two, and by adding the one test that
  reaches the key-presence branch alone.
- The `is_file` line in `_will_not_parse` exists because the first version used
  `exists()`, and **two existing tests caught it**: both make the settings path
  a directory to force a write failure, and both were suddenly told the file
  that would not load could not be set aside. A directory has no contents to
  lose, so it is not a file to preserve.

## The sixth pass: the blast radius, and the first round with no high

Cold, lens: what the changed `AppSettings` contract does to everything outside
`app_settings.py` and the Plan screen — twenty-odd screens load and save their
own settings object. **Two mediums, three lows, and no high.** Both mediums are
fixed here.

- **Medium: seven Save buttons reported a write that had refused.** `save`
  returns False and writes nothing when a settings file is present, will not
  parse, and cannot be copied aside. Eleven call sites; one acted on it. Two of
  the seven did more than print: **Appearance** also ran
  `self.app.settings = self.settings` and applied the theme app-wide, so the
  user saw a theme the file did not hold and lost it on the next launch, and
  **Email Import** reloaded launchd from the unwritten file, handing the
  importer the old interval while reporting the new one. All seven now go
  through `SettingsScreen._write_settings`, which reports the refusal on that
  section's own label and returns False so the caller skips the rest.

  This was the finding round 4 recorded in `BACKLOG.md` rather than fixing,
  with the reason that it touches every settings surface. Round 5 widened it:
  the refusal used to need an object that knew its own load had failed, and now
  an object that loaded fine can be refused, because `save` reads the file. A
  gap I widened twice was no longer one to record a third time.
- **Medium: the Plan screen's warning named a cause it could not know.** "has
  not been confirmed since the settings file could not be read" was written for
  the corrupt-file case and shipped as the wording for all three states that
  reach it — and the common one, a settings file from a version with no Day
  Settings, reads perfectly. The round-4 note in the code claimed "the wording
  says what is true in every state it can appear in"; round 5 made that false
  and nothing noticed, because the only test asserted the substring both
  wordings share. No cause is named now.
- **Low, recorded:** a full disk makes the refusal name a remedy that cannot
  work; `TimerWindow`'s long-lived settings object is unreachable from the Plan
  screen only because of its Tk parent; and the three remaining `save()` call
  sites fail silently rather than wrongly.

**Also found by running the suite, not by any pass:**
`test_the_date_is_a_picker_not_a_free_text_entry` compared the date picker,
which `__init__` builds from `date.today()`, against a date the fixture had
assigned behind it. It passed only on the day it was written and went red at the
first midnight of this session. Fixed, and the other 24 `date.today()` uses in
`tests/` are recorded as unaudited.

Five mutations, five reds, plus two repairs to tests round 5 had weakened:
`test_an_unreadable_settings_file_is_flagged_not_just_printed` could no longer
tell its own branch from the missing-file branch (both now set the field), so it
asserts the parse error reaches the log as well; and
`test_a_readable_file_is_not_copied_aside_on_every_save` had lost its only
precondition when the `settings_unreadable` assertion went.

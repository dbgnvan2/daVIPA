### The three tests worth having

- **`test_prim22_every_factor_combination_is_capped`** walks all 256
  combinations, asserting `min(product, 9999)` for each with **exact counts**
  (223 unchanged, 33 clamped) rather than a floor. It then asserts what makes
  the clamp detectable at all: the raw products jump straight over the cap —
  `{12800, 25600, 51200, 102400}` above it, 6400 the highest below — so no
  combination lands on 9999 by arithmetic, and every stored 9999 is therefore a
  capped one. Without the whole product set there is nothing to notice: the
  range 6401–12799 contains no reachable score.
- **`test_prim11_renumbering_a_scale_moves_its_floor`** monkeypatches a scale
  whose minimum is 7. With the scales as shipped every floor is 1 or 2, so a
  hard-coded `1`/`2` in `floor()` passes the plain minimum test. Mutation D
  proves exactly that: hard-coding `1,1,2,2` leaves
  `test_prim11_the_floor_is_the_minimum_of_each_scale` **green** and takes only
  the renumber cases red. PRI-M1.1 is the claim that renumbering moves the
  floor, and this is the only test that can see it.
- **`test_prim25_only_one_function_multiplies_the_factors`** parses the three
  modules and asserts an **exact count of 0** four-factor products outside the
  one scorer — parsed, not grepped, and counted exactly, per the repo rule. It
  ships with a positive control, `test_prim25_the_product_detector_finds_a_product`:
  without it, a detector that silently matched nothing would pass the guard for
  the wrong reason, which is the "looks right but is wrong" input (P7).
  Mutation F confirms the control is load-bearing.

PRI-M1.6 is a dirty-state test (P8) — written, re-read, cleared, updated,
re-read, updated again — so the second update sees persisted state rather than
the object the first call was handed. PRI-M1.7 and PRI-M1.8 are a deliberate
pair: the new-item form must show the floor, the editor on an existing unscored
row must not. PRI-M2.6 is asserted at **both** render sites, driven as
behaviour, because PRI-M2 exists to stop those two drifting apart.

Every `DatabaseManager` and `VPSManager` takes an explicit `tmp_path` database.
No mapped window is added: `conftest.py` silences `grab_set` and withdraws
every window on creation, and `ItemEditorDialog.__init__` withdraws itself, so
the suite's documented mapped-window count is unchanged.

## The cold pass

One cold pass over `6009b0d..f3937d3`, scoped to test quality, whether each
test verifies its criterion, the repo rules, and the accuracy of every factual
claim in the batch's prose. **Two mediums, both real, both fixed; four lows,
three fixed and one filed.** It independently recomputed PRI-M2.2's numbers —
256 combinations, 223 unchanged, 33 clamped, the clamped raws exactly
`{12800, 25600, 51200, 102400}`, 6400 the highest below, 9999 unreachable —
and every one was right. It also corrected the range: four commits, not five;
`6009b0d` is the base.

**Medium 1 — the PRI-M2.5 guard was blind at the one site it exists to
protect.** The detector filtered operands by name
(`{importance, urgency, size, value}`), while
`screens/inline_editors.py::update_score` already binds its four factors as
`i`, `u`, `s` and `v`. A re-introduced `i * u * s * v` at that render site
would have left the guard green at an exact count of 0 while a second scorer
existed — and PRI-M2's whole purpose was that those two labels cannot disagree.
Widening the name list only moves the blind spot to the next names someone
picks, so the filter is gone: the walk now matches **any** four-operand product
anywhere in the module. That is achievable because the three modules contain no
four-operand product of any kind, measured rather than assumed. The cost is
stated in the test and in its failure message — an unrelated four-way product
added to one of them fails this guard, and the answer is to narrow it
deliberately, never to raise it above 0. Four positive controls now cover four
namings including the single letters, plus one for `skip_functions`, which
nothing else in the file could see because the function it excuses holds no
four-way product. Mutations G and H, in the Verification section above, prove all five load-bearing: with
the name filter back, four tests go red.

**Medium 2 — three live claims that the test this batch turned green is still
red**, all in `BACKLOG.md`'s first section, which the file's own header calls
"what `main` needs to go green". One of them told the next pusher they "ship

`NOTES.md`, and left the three duplicates standing — the exact failure mode the

  exists to keep the score column four digits wide; nothing yet proves
  `"P:9999"` fits at the larger selectable row font sizes, and the five screens

  closed by writing PRI-M3.1's test alone.
- **`PRI-A1`–`PRI-A4`** are promised by the PRI plan and the documentation
  index and exist in no backlog. `SSC-1` stays open for that half.
- All four tests in `tests/test_priority_floor_form.py` build real
  `ItemEditorDialog` or `InlinePriorityDialog`
  windows. They are withdrawn and `grab_set` is silenced by `conftest.py`, so
  they need no display beyond Tk itself and are skipped where Tk cannot start —
  but they are the slowest tests in the two files (3.8s against 2.0s), and that
  is the cost of checking the labels as behaviour rather than through a stub.
- `test_prim25_only_one_function_multiplies_the_factors` scans three modules by
  name. A fourth module that grew its own copy of the product would not be
  seen. The honest widening is a list derived from the importers of
  `priority_score_from_factors`, which is not written. **This was the shallower
  half of the gap.** The cold pass found the deeper one: the detector filtered
  operands by name, so a product written `i * u * s * v` — exactly how
  `screens/inline_editors.py::update_score` already names its four factors —
  left the guard green at count 0, at the one render site PRI-M2 exists to
  protect. The name filter is gone; the walk now matches any four-operand

  message: an unrelated four-way product added to one of them fails this guard

  The batch's own plan had anticipated this ("narrow the walk to products of the
  four *factor variables*, **stated in the test**"); the narrowing was applied
  and not stated, which is how it went unnoticed.
